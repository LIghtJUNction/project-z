---
name: zuse-skill-creator
description: Create importable Zuse GUI modules with native function descriptions, explicit application scope, Zuse 0.5 guarded draft writes, bounded output, and tests for independent calls and honest application support metadata.
---

1. Read only the applicable module and current runtime schema. Add `skills/<id>/SKILL.md` and `module.zuse`; add its public names, ordered parameters, backend and read-only policy to `catalog.json`.
2. Place a concise `///` description immediately before every exported `fn`. Native `functions()` reads these comments. Zuse function parameters are names, not typed declarations; builtin calls validate values after native AST substitution. Keep untrusted strings as parameters, never concatenate them into executable source.
3. Import modules through the native `import` command. Modules contain declarations only; importing must not launch a browser, observe the desktop or perform input. Do not implement a second language parser in a wrapper.
4. Require explicitly verified application/window scope. Prefer exact semantic targets to coordinates. Reject ambiguous, stale or unsupported targets. Never replace missing background access with a focus change, system pointer, another application or another account. Native writes require stable object identity, dispatch-time scope checks and a no-focus contract; numeric accessibility paths alone do not provide that.
   For an empty draft, use `accessibility.set_text` with `expected_text=""` and the observed `expected_pid`, retain its same-object readback receipt, and observe the editor afterward. Keep preparation and sending in separate functions. State that text checks and writes are separate application calls and that PID identifies a process, not a conversation. Require explicit send authorization and fresh target/draft verification; a native action receipt does not prove delivery.
5. Keep discovery concise. `functions(namespace="…")` selects one module. An adapter can project bounded fields, but must not claim that all accessible names are free of user content. A truncated observation is incomplete evidence, not proof of absence.
6. For parallel work, use separate owned sessions and preflight all branches before starting any. Keep native desktop writes and sends outside the adapter's parallel batches. Do not share mutable browser/runtime state without an explicit serialization model. Use the host's authorized computer tools for real desktop interaction; execution tools are only appropriate for owned, isolated fixtures.
7. Test native import/metadata, malformed or effectful imports, argument injection, ambiguity, unavailable backends, output bounds and branch isolation. Run `python3 zskills.py check` and `ZUSE_BIN=/path/to/zuse python3 -m unittest discover -s tests -v`. Run the opt-in browser tests where Chromium can start normally.
8. Record the exact runtime and environment. Separate parser/preflight tests, mock receipt projections, owned fixture results and real application acceptance. Report shipped mechanisms with `implemented`, and keep `application_accepted:false` / `blocked` when target access is missing. Probe guarded-call support separately from module import. Preserve historical validation receipts. Commit source to Git; do not publish account data, profiles, compiled binaries or an unsupported success claim.

`zuse_capabilities()` is a read-only native probe; it does not itself grant input permission or establish application identity.
