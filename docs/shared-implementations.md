# 共享能力与重复实现

同一生产行为应由一个明确的实现负责，消费者通过稳定接口复用它。新增实现前先核对现有 Project Z 库；确有多个消费者需要同一能力、现有库又不适合承载时，再抽取独立库。是否抽库取决于共同契约和维护边界，不能只按相似行数或函数名称决定。

本规则约束后续开发和验收，不表示现有仓库已经完成去重。一次迁移的完成范围由实际接入的消费者及其验证记录决定。

## 1. 先证明哪些内容相同

提案要列出具体仓库、提交、文件和调用位置，再比较输入、输出、错误、资源使用和平台要求。关键词搜索或文本相似度只能帮助定位候选，不能代替这个比较。

| 候选情况 | 判断依据 | 处理方式 |
| --- | --- | --- |
| 多个消费者各自维护同一生产逻辑 | 共同的输入、结果、失败语义和修复需求；有实际调用者 | 优先接入现有提供者；缺少合适提供者时抽取共享核心，并迁移实际调用 |
| 两处使用相同标准算法 | 算法名称相同，但数据表示、侧信道要求、性能约束或协议语义可能不同 | 核对契约后决定；不能仅凭算法相同认定必须合并 |
| 不同操作系统、设备或运行时的后端 | 共用用户可见契约，底层 API、生命周期或可用能力不同 | 共享契约和可共享逻辑，保留必要后端及对应平台验收 |
| 测试夹具、黄金结果或独立参考实现 | 是否需要独立于被测实现才能发现共同错误 | 可共享无行为的数据与构造工具；保留独立预期值和验算路径 |
| 生成代码、协议绑定或第三方源码 | 生成器、上游版本、许可证和本地修改边界 | 维护明确的生成源或上游来源；不靠手工合并生成结果制造新副本 |
| 短小适配层或只有一个当前使用者的辅助函数 | 是否存在可独立描述的公共契约，以及引入依赖后的实际成本 | 保持局部内聚；不为消除几行相似代码单独增加 crate 或循环依赖 |

对需要保留的两份实现，记录差异所在及其验证方式。“跨平台”或“测试需要”本身不足以解释所有重复；说明具体平台约束或独立验算目的即可，不要求为形式补充空泛理由。

## 2. 选择一个能力提供者

先从 `catalog.json`、`.gitmodules`、`project-z.toml` 和现有源码找候选，核对包的实际职责与使用位置。项目名称前缀不证明归属；库的存在也不证明其 API 已满足当前需求。

复用现有库时，对照以下边界：数据与编码约定、错误类型、取消和超时行为、线程与所有权、输入和资源上限、默认特性、`no_std` 要求、最低 Rust 版本、系统依赖及许可证。消费者需要的薄适配层可以保留，但适配层不应再次实现已交给公共库负责的解析、编码或状态转换。

新建独立库时，列出真实消费者、共同契约、维护负责人和迁移顺序，并说明为什么已有库或同仓模块不能合适地承载该能力。避免引入依赖环、将应用状态反向塞进基础库，或为了一个小调用迫使所有消费者引入无关运行时和平台依赖。

接口变化由提供者和消费者共同推进。不要为了暂时让消费者编译，通过复制提供者源码、固定旧内部版本或私设 path/registry 覆盖绕过适配。内部来源与对外发布投影继续遵循 [AGENTS.md](../AGENTS.md) 和[协同维护规则](../CONTRIBUTING.md)。

## 3. 迁移真实调用

1. 记录基线提交、重复位置、现有调用者和应保持的行为。需要改变行为时单独写明变更与验收预期。
2. 确定提供者和公共接口，补足能区分旧问题与正确行为的必要测试。测试仍应包含独立的预期值或参考依据。
3. 在完整的独立快照中运行 `python3 scripts/project_z.py impact --repositories <仓库或包>`，检查直接、间接、运行时及安装消费者；补齐漏登记关系，并协调各仓库现有负责人。
4. 按依赖顺序接入消费者，迁移实际执行路径。兼容包装只保留接口映射；删除已迁走的生产实现，或者明确记录尚未迁移的位置和阻碍。
5. 按现行来源规则更新消费者声明、Cargo.lock 和嵌套 gitlink。先完成子仓库的必要本地验证、提交与远端读回，再由聚合维护者更新完整快照和生成索引。
6. 对实际变化执行对应的本地行为门禁，再完成聚合 `check` 和 `resolve --all`。GUI、设备、服务、ABI、安装和发行验证按受影响范围保留。

上述 `impact`、`check` 和 `resolve` 当前会读取 Cargo metadata，需要完整检出和相应工具链。开发机上的相关 Cargo 批次由最外层统一持有共享锁；不要在脚本内部再次获取同一锁。仅需规划已记录快照时，可使用 `maintenance.py --require-catalog` 的审计结果，但该审计不代替完整快照验收。

## 4. 验收要能回答的问题

| 门禁 | 需要保留的证据 |
| --- | --- |
| 共享边界正确 | 原实现位置、提供者位置、双方提交；共同契约及必须保留的差异 |
| 消费者实际接入 | 调用位置和依赖变更；被替代实现的删除或明确的剩余清单 |
| 来源一致 | 规范的内部 Git 声明、实际锁定提交与版本、嵌套 gitlink；完整快照的检查结果 |
| 行为得到验证 | 命令、源码提交、环境、退出码、关键断言与未覆盖范围；与本次变化相关的正向、边界及失败路径 |
| 必要差异得到保护 | 平台后端、特性组合、最低工具链、独立测试预期或兼容接口的具体验证 |
| 传播完成或阻碍可接手 | 每个消费者的完成状态；未完成项的实际原因、负责人、可复用提交和下一步 |

不要删除失败测试来满足迁移目标，也不要把调用了同一段代码当作已经独立验证它。保留旧算法作为测试参考时，注明其来源和用途，避免它重新进入生产调用路径。

源码和相关环境没有变化时，可以明确复用已有验证，但需给出可核对的提交或文件校验值及原始记录。复核历史记录、重新运行测试、实际运行应用是不同证据，不能相互冒充。减少代码行数、crate 数或重复片段数，也不能单独证明运行速度、内存占用或可靠性改善；需要这类结论时另附匹配的测量。

## 5. 记录模板与剩余工作

每次共享实现迁移在变更说明或验收文档中填写以下信息，链接现有材料即可，无需复制整份日志。

| 项目 | 填写内容 |
| --- | --- |
| 能力与契约 | 要统一的行为、输入输出和失败边界 |
| 基线与提供者 | 仓库、完整提交、源码位置、负责人 |
| 选择依据 | 已有候选、选择原因、依赖成本和必要差异 |
| 消费者 | 实际使用者及反向依赖；每个消费者的迁移提交 |
| 验证 | 实际执行或复用的记录、退出码、关键断言、未覆盖范围 |
| 剩余实现 | 保留位置、原因、负责人，以及重评或迁移的具体触发条件 |
| 集成状态 | 本地修改、已提交、已推送、聚合验证、正式发布分别处于什么状态 |

临时保留的重复生产实现应有可追踪的后续项。完成了公共库或单个消费者，只能报告该部分完成；其余消费者仍需迁移或明确交接。必要的平台差异和独立测试参考可以长期保留，前提是其职责清晰且有对应验证。

现有自动检查能够核对来源、锁和依赖图，不能判断所有语义重复。维护者需要结合以上证据审查共享边界；不以简单的相似度阈值作为拆库或合并实现的硬门槛。
